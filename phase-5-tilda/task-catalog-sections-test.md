**Статус:** ✅ ЗАКРЫТА 20.08.2026 (тест пройден на trial-аккаунте Personal)
**Кто делал:** Оля
**Когда:** 20.08.2026
**Что блокировало:** оценку трудоёмкости Phase 5 и решение ОВ36
**Дата постановки:** 17.08.2026

## Зачем

По ДМ02 и ДМ26 каталог имеет четыре параллельных входа: по типу препарата, по культуре, по вредному объекту, по действующему веществу. В URL-схеме (`catalog-ia-v1.md` §7) каждое значение словаря — отдельная страница с читаемым адресом:

```
/catalog/kultura/pshenitsa/
/catalog/vrednyy-obekt/septorioz/
/catalog/dv/glifosat/
```

При словарях в несколько десятков культур, до двух сотен вредных объектов и несколько десятков ДВ это **190–310 страниц**. Если каждую придётся заводить и настраивать руками — это больше, чем весь остальной сайт вместе с 87 карточками, и сопровождать такое при каждом изменении ассортимента нереально.

**Но по документации Tilda похоже, что руками не придётся.** Механика разделов каталога закрывает большую часть задачи:

- товар может принадлежать нескольким разделам и подразделам одновременно — значит один препарат попадает и в «Гербициды», и в «Пшеница», и в «Глифосат»
- вложенность до 10 уровней — хватает на схему «По культуре → Пшеница»
- принадлежность разделам назначается массово (выделить товары → действие) и задаётся при импорте CSV
- блок ST340 умеет динамически подставлять название и описание из настроек раздела — тексты страниц не пишутся по одной

Чего документация не говорит: **какой адрес получает страница раздела** и можно ли задать разделу собственные мета-теги. В настройках каталога указывается адрес, от которого начинаются все ссылки, и он родительский для разделов — но конкретный вид URL по справке не восстановить.

Это и есть развилка. Умозрительно её не закрыть — нужен получасовой эксперимент в живом аккаунте.

Варианты, в порядке предпочтения:

**Что подготовить заранее (не требует доступа):**

## Что проверяем — чек-лист

Каждый пункт — да/нет плюс скриншот или пример адреса.

### Адреса и SEO

1. **Какой URL получает страница раздела.** Читаемый (`/catalog/kultura/pshenitsa/`) или служебный вида `/catalog/tproduct/...`
2. **Можно ли задать разделу свой slug** — или адрес формируется платформой автоматически из названия
3. **Есть ли у раздела свои мета-теги** (title, description) или они наследуются от страницы, на которой выведен блок с товарами
4. **H1 на странице раздела** — подставляется ли из названия раздела (опция ST340) или задаётся вручную на странице
5. **Дубли.** Товар в трёх разделах — сколько адресов у его карточки. Если несколько, есть ли canonical

### Мультипринадлежность

6. **Товар в нескольких разделах одновременно** — корректно ли выводится во всех
7. **Хлебные крошки при мультипринадлежности** — какой путь показывается в карточке товара, настраивается ли
8. **Вложенность:** раздел «По культуре» → подраздел «Пшеница». Как выглядит адрес подраздела, наследует ли путь родителя
9. **Скрытие раздела из навигации и фильтров** (галочка в настройках раздела) — что именно скрывает

### Массовые операции

10. **Импорт CSV с разделами:** в каком поле указывается раздел, поддерживаются ли несколько разделов в одной ячейке и каким разделителем
11. **Массовое назначение раздела** выделенным товарам — работает ли для сотни позиций
12. **Экспорт-правка-импорт** как способ обновления: не создаёт ли дубли товаров при повторном импорте

### Совместимость с остальными решениями

13. **Фильтры вместе с разделами** (ДМ23) — работают ли штатные фильтры внутри страницы раздела
14. **Сортировка** на странице раздела — есть ли «А-Я» (дефолт по ОВ13)
15. **Единый шаблон карточки** — подтвердить, что шаблон один на все категории (это уже зафиксировано в `tilda-constraints.md` §5, проверка на живых данных)

## Возможные исходы

| Исход | Что означает | Что делаем |
|---|---|---|
| **Адреса читаемые, мета настраиваются** | Риск снят полностью | Все параллельные входы делаются разделами каталога; ручной работы почти нет; ОВ36 закрывается |
| **Адреса читаемые, мета общие** | Страницы есть, но SEO-потенциал ограничен | Разделы для всех значений + ручные посадочные с уникальным текстом только для приоритетных |
| **Адреса служебные** | Механика разделов для SEO не годится | Возврат к варианту из инвентаризации: ЧПУ вручную для приоритетных значений (≈50 страниц), хвост словаря — через фильтр с параметром в URL |

В любом исходе результат — фактическая оценка объёма Phase 5 вместо диапазона «от 105 до 400 страниц».

## Результаты теста — 20.08.2026

**Кем:** Оля (Тильда) + Claude (интерпретация).
**Где:** trial-аккаунт Personal, свежий сайт «Восток АгроХим», домен `sixth-eased-comb.tilda.ws`.
**Что импортировали:** `test-import-catalog-v1.csv` (8 SKU, 52 значения Category, мульти-значения через `;` в кавычках) + `test-import-single-category.csv` + `test-import-multirow-category.csv` (уточнения формата).

### По пунктам чек-листа

**Адреса и SEO**

| # | Пункт | Результат |
|---|---|---|
| 1 | URL страницы раздела | **Гибридный по умолчанию:** `/{ID}-{транслит}` (например `/846461681704-gerbitsidi`). Читаемый, но с числовым префиксом. Полный ЧПУ достигается ручным редактированием поля «АДРЕС РАЗДЕЛА» — цифровой префикс убирается, остаётся только транслит. |
| 2 | Свой slug раздела | **Только вручную в UI** (поле «АДРЕС РАЗДЕЛА» настроек раздела). Через CSV нельзя — отдельного поля для слага раздела в списке импорта нет. |
| 3 | Свои мета-теги раздела | **`<title>` подставляется автоматом из названия раздела.** `<meta description>` пустой; штатных полей для description раздела нет. Обходной путь — «Специальная страница раздела» (в доп. настройках): при её создании адрес и мета раздела берутся со страницы. |
| 4 | H1 на странице раздела | **Не подставляется автоматически.** На стандартной странице раздела заголовок «Гербициды» не выводится — только карточки товаров. Заголовок нужен блоком на странице (или через спецстраницу раздела). |
| 5 | Дубли карточки при мультипринадлежности | **У товара один canonical**, на его собственный URL. У раздела свой canonical на самого себя. Балерина, привязанная к двум разделам, имеет один адрес `/catalog/balerina-se/` и один canonical. |

**Мультипринадлежность**

| # | Пункт | Результат |
|---|---|---|
| 6 | Товар в нескольких разделах | **Работает.** Балерина одновременно в «Гербициды» и «Пшеница», выводится в каждом. |
| 7 | Хлебные крошки при мультипринадлежности | Идут **по UI-иерархии разделов** (родитель, установленный в поле «Находится в разделе»). Пример: «Восток АгроХим / Каталог / Гербициды / Пшеница». Есть отдельное поле «Название раздела в хлебных крошках» — можно кастомизировать текст. |
| 8 | Вложенность | В UI задаётся через «Находится в разделе». **URL иерархию не наследует автоматически** — задаётся вручную в поле адреса через `/`. Пример: `/gerbitsidi/pshenitsa`. Лимит — 9 уровней вложенности, включая адрес каталога (сообщено самим интерфейсом). |
| 9 | Скрытие раздела из фильтров/навигации | **Есть галочка** «Скрыть раздел в фильтрах/навигации» в доп. настройках раздела. |

**Массовые операции — критично для проекта**

| # | Пункт | Результат |
|---|---|---|
| 10 | Формат Category в CSV | **Только одно значение на строку.** Мульти-значения через `;`, `,`, пробел, `\|` **не парсятся** — вся строка воспринимается как имя одного раздела и не находится. **Множественная привязка — дублями строк** с одинаковым `External ID` и разными `Category`; Тильда объединяет в одну карточку. |
| 10a | Разделы существуют до импорта | **Обязательно.** Тильда не создаёт разделы на лету — молча игнорирует несуществующие значения Category. |
| 11 | Массовое назначение раздела | **Работает** при выполнении условия 10a. Проверено на 8 товарах одним импортом. |
| 12 | Экспорт-правка-импорт | Не тестировали (штатная функция, документирована). |
| 13 | Фильтры + разделы | Не тестировали (штатная функция). |
| 14 | Сортировка | Не тестировали. По документации доступны «А-Я», по цене, по новизне; «по популярности» нативно нет (ОВ13). |
| 15 | Единый шаблон карточки | **Подтверждено.** Товары 7 разных категорий выводятся через один шаблон каталога. |

### Побочные находки

- **URL товара из CSV подхватывается корректно.** Поле «Ссылка на страницу товара» в CSV становится итоговым адресом карточки. Наш `/catalog/balerina-se/` из CSV работает без изменений. Значит **все 87 карточек товаров получат человекочитаемые URL за один импорт**.
- **Фото по URL с satom.ru не подгружаются** — satom-CDN отдаёт 403 для запросов с IP Tilda. При боевом импорте фото загружать в CDN Tilda предварительно (либо использовать локальные `parsed_v2/photos/`).
- **Валюта по умолчанию** — доллары; поменять на рубли в настройках каталога.
- **Обязательный шаг перед проверкой разделов:** создать любую страницу с блоком каталога (например ST300) и назначить её главной в настройках каталога, иначе адреса разделов не работают.

### Ответ на ОВ36

Раньше вилка была: 190–310 значений словарей → либо страницы каталога Тильды (если работают ЧПУ и мета), либо ручные посадочные (если нет).

**Теперь: работают ЧПУ + иерархия + свой slug + автоматический `<title>` + один canonical у товара.** Для проекта это значит:

1. **Все ~190 значений получают собственные страницы разделов** каталога Тильды. Ручных посадочных не нужно. Адреса читаемые (после ручного редактирования slug'а).
2. **Приоритетные 30–50 значений** (топ-культуры, топ-ДВ) дополняются **спецстраницами** — для полного контроля мета-описания и уникального контента. Остальные ~140 значений остаются на автогенерируемом шаблоне со своим slug'ом.
3. **Массовое проставление slug'ов** — через API (Business+) скриптом. На старте (Personal-триал, потом Personal клиента) — руками, ~30 сек на раздел = ~100 минут на 190 разделов. Приемлемо как разовая работа при первичной сборке.
4. **Импорт товаров** — многострочный CSV, где каждая строка = одна привязка «товар → раздел». Для 87 SKU × ≈8 разделов на товар ≈ **700 строк**, генерируется скриптом из готовых маппингов за секунды.

**Пересчёт оценки Phase 5** (только по каталогу, без вёрстки шаблонов):
- Создание 190 разделов вручную с slug'ами и иерархией: 3–4 часа
- Генерация CSV из маппингов + импорт товаров: 1 час
- Создание 30–50 спецстраниц с уникальным контентом для приоритетных значений: 5–10 часов (зависит от глубины)
- Итого сборка каталога: **9–15 часов работы** (не считая вёрстки самих шаблонов ST-блоков и карточки товара).

Против ранее ожидавшихся 105–400 «страниц» — теперь **~50 страниц реальной сборки максимум** (главная, служебные страницы, спецстраницы приоритетных значений). Всё остальное — админка каталога.
